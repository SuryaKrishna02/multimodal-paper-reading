Primer: the Thinker writes text, the Talker writes speech

  • Inherited from MiniCPM-o 4.5Realtime-Venus keeps the architecture of this open 9B model (the shaded area). It adds the delegate path.
  • ThinkerThe language model. It reads the encoded audio and video, decides to listen or speak, and writes the reply text.
  • TalkerA 0.3B autoregressive Llama decoder. It reads the hidden states and the reply text of the Thinker. It writes S3 speech tokens one by one. A flow-matching decoder turns them into the audio that the user hears.
  • One meaning, two outputsThe Thinker decides what to say and how. So the Talker can stay small (0.3B) and focus only on speech.

Memory keeps only the frames that change

An hour of video does not fit in the context window. A training-free gate stores a frame in long-term memory only if it changed enough since the previous frame. A dropped frame is still used in the short-term context.

  • Motion matchingEach 8×8 pixel block first looks for its best small shift in the previous frame (block motion matching). A camera pan then gives a low change score, so the same street is not stored again and again.
  • Local-change protectionA small event, such as a short flash, barely moves the average score. If any one block changes a lot, the frame is kept anyway.
  • Max drops in a rowAfter this many dropped frames in a row, the next frame is kept anyway. Memory never has a long gap.

Sec 4.2Fig 5

Retrieval balances relevance and novelty

  • 1. Relevance: MaxSimThe question is split into tokens. Each token takes its best cosine match among a frame's visual tokens. The weighted sum of these best matches is the frame's relevance.
  • 2. Token weights: MAD"Who" and "hands" match every frame about the same, so they cannot tell frames apart. MAD (median absolute deviation) measures how much a token's score varies across frames: more variation, more weight.
  • 3. Novelty, then the pick (MMR)The top 5 by relevance are candidates. Novelty: how different a candidate looks from higher-ranked ones (a near copy gets 0). Score = (1 − w) relevance + w novelty. Keep the top k.

Try: Move the novelty weight above 0.7 and look at the repeated scene at 18:20. Then clear "MAD token weights".

Step 3 is the MMR rule: λ·relevance − (1 − λ)·similarity to frames ranked above. With novelty = 1 − similarity, w = 1 − λ. The paper does not give its λ.

Limitations, takeaways, discussion, and further reading.

Limitations, as the authors state them

  • Two video benchmarksOn ProactiveVideoQA and WorldSense, the Omni model scores lower than MiniCPM-o 4.5.
  • No component ablationsThe results do not isolate each training component. That needs controlled ablations.
  • InterruptionsThe interruption response rate is lower than Joy-Duplex, GPT-4o, and Gemini 3.1 Live.
  • Tool argumentsArgument accuracy and Pass@1 stay below GPT-Realtime.
  • Delegate evaluationThe benchmark checks only the routing decision, not the task result.
  • Future workShorter chunks, longer context, and recovery from slow or failed tool calls.

Sec 7.3Sec 7.5Sec 7.6Sec 8

Takeaways

  • One timelineIt holds user input, model output, delegate requests, and backend results.
  • Split rolesThe frontend decides when to listen, speak, or delegate. The harness does the slow work and writes the reply text.
  • Frozen evidenceCapture freezes the evidence at the request time. Later events cannot change the task.
  • Strong and weakContinuation under backchannels and background speech is strong. Delegation decisions are still weak.

Sec 3 to 8

Discussion

  1. The harness writes the reply text, but the frontend decides when to speak it. Is this the right split? What can go wrong when the conversation moves on?
  2. The Audio model delegates too much, and the Omni model delegates too little. Which error costs a user more? Should a learned token or a separate router make this decision?
