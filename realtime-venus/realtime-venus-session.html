Primer: full-duplex dialogue in one-second chunks

A turn-based system speaks or listens, but not both. A full-duplex model does both. Realtime-Venus cuts time into one-second chunks. In each chunk, the model reads new input and writes one decision.

A backchannel must not stop the assistant. An interruption must stop it.

Primer: the Thinker writes text, the Talker writes speech

Realtime-Venus starts from MiniCPM-o 4.5, an open 9B model.

The Thinker is the language model. It reads audio and video tokens and writes text.

The Talker reads the hidden states of the Thinker. It writes S3 speech tokens. A flow-matching decoder turns these tokens into a waveform.

Text and speech share one meaning. The speech side does not need its own language model.

Core idea: a fast frontend and a slow harness on one timeline

The frontend keeps the conversation alive. The harness does the slow work in the background. Both write to one causal timeline.

\[ O_k = (c_k,\, Y_k,\, D_k,\, S_k) \]

Both frontends use this step. The index \(k\) counts one-second chunks. The frontend \(m\) is audio or omni.

Only \(Y_k\) and \(S_k\) reach the user. The other outputs stay private.

Eight tokens control the conversation

TokenJob
<|listen|>Continue to perceive. Do not speak.
<|speak|>Generate foreground text and speech now.
<|chunk_eos|>Close the speech of this chunk.
<|turn_eos|>Close the assistant turn.
TokenJob
<delegate>Open a private task request.
</delegate>Close the task request.
<backend>Open a harness result. It is input, not a target.
</backend>Close the harness result.

The model writes the delegate span in natural language. The host hides it from the screen and from speech. The paper adds the four new tokens to the tokenizer, the input embeddings, and the LM head.

The scheduler paces text to match speech playback

\[ n_k = \arg\min_{n} \left| \tau_{k-1} + \mathcal{D}(Y_{k,1:n}) - t_k \right| \]
  • \( t_k \) The end of chunk \(k\).
  • \( \tau_{k-1} \) The end time of the speech that the model scheduled before.
  • \( \mathcal{D}(Y_{k,1:n}) \) The estimated speech time of the first \(n\) text tokens.
  • \( n_k \) The number of text tokens for this chunk.

When speech lags, the model writes fewer tokens. When playback has room, it writes more.

One policy for control, text, and delegation

\[ p_{\theta,\phi}(O_{1:K} \mid U, B) = \prod_{k=1}^{K} p_\theta(c_k, Y_k, D_k \mid U_{\le k}, B_{\le k}, O_{<k})\; p_\phi(S_k \mid H_{\le k}, Y_{\le k}, S_{<k}) \]
  • \( U, B \) User audio features and sparse backend results.
  • \( p_\theta \) The LLM. It predicts the control token, the text, and the delegate text.
  • \( p_\phi \) The speech decoder. It predicts speech tokens from the LLM hidden states \(H\).

The control token comes from the same representation as the reply. Thus, the model can treat a similar sound in different ways, by its role in the conversation.

Backend results are inputs, not predictions. Training updates only the Thinker. The acoustic decoder stays fixed.

Capture freezes the evidence at the request time

\[ X_i = \mathrm{Snap}(\mathcal{B}^{\sigma};\, \kappa_i,\, \Delta) \]
  • \( \mathcal{B}^{\sigma} \) The bounded buffer of session \(\sigma\).
  • \( \kappa_i \) The time \(T_i\) of the opening token and the last input at that time.
  • \( \Delta \) The look-back horizon.

Later observations cannot change \(X_i\). Assistant speech enters only if its playback was confirmed by \(T_i\).

Limitations, as the authors state them

  • On ProactiveVideoQA and WorldSense, the Omni model scores lower than MiniCPM-o 4.5.
  • The results do not isolate each training component. That needs controlled ablations.
  • The interruption response rate is lower than Joy-Duplex, GPT-4o, and Gemini 3.1 Live.
  • Argument accuracy and Pass@1 stay below GPT-Realtime.
  • The delegate benchmark checks only the routing decision, not the task result.
  • Future work: shorter chunks, longer context, and recovery from slow or failed tool calls.

Takeaways

  • One timeline holds user input, model output, delegate requests, and backend results.
  • The frontend decides when to listen, speak, or delegate. The harness does the slow work and writes the reply text.
  • Capture freezes the evidence at the request time, so later events cannot change the task.
  • Continuation under backchannels and background speech is strong. Delegation decisions are still weak.

Sec 3 to 8

Discussion

  1. The harness writes the reply text, but the frontend decides when to speak it. Is this the right split? What can go wrong when the conversation moves on?
  2. The Audio model delegates too much, and the Omni model delegates too little. Which error costs a user more? Should a learned token or a separate router make this decision?
